# DMA_ATTEMPT — попытка перевода SDIO на DMA: откат

**Дата:** 09.11.2026
**Статус:** ❌ Отказ. Возврат к блокирующему режиму `HAL_SD_WriteBlocks` / `HAL_SD_ReadBlocks`.
**Затронуто:** `src/diskio.c`, конфигурация SDIO (`src/sdio.c`).

---

## 1. Цель попытки

Снять CPU с ожидания во время передачи на SD: заменить синхронные вызовы в `diskio.c` на асинхронные `HAL_SD_WriteBlocks_DMA` / `HAL_SD_ReadBlocks_DMA`, чтобы момент коммита чанка VIBL (~12 КБ) не блокировал главный цикл.

## 2. Корневая причина — баг STM32F4 HAL (SD-модуль)

Выявлена гонка состояний в обработчике прерываний SDIO (`HAL_SD_IRQHandler`):

- Флаг **DATAEND** (конец передачи данных по шине SDIO) очищается/обрабатывается **до того, как DMA завершает перенос буфера**.
- То есть момент «данные ушли на карту» и момент «DMA дописал последний байт в память / дочитал из памяти» рассинхронизированы: прерывание SDIO срабатывает раньше, чем DMA-транзакция фактически завершена.
- Последствие: конечный автомат HAL **не переходит в готовое состояние** и навсегда остаётся в `HAL_SD_STATE_BUSY`. Все последующие вызовы `HAL_SD_*` возвращают BUSY/timeout — драйвер «мёртв» до сброса MCU.

Это дефект самого HAL-модуля SD для F4, а не нашей конфигурации: воспроизводилось независимо от ширины шины и режима FIFO.

## 3. Пробованные обходные пути (все без стабильного результата)

| № | Мера | Результат |
|---|------|-----------|
| 1 | Включение SDIO **FIFO** (буферизация данных в периферии) | Не устранило рассинхрон DATAEND/DMA; зависание в BUSY сохранялось |
| 2 | Перебор **burst-режимов** передачи | Нестабильно: часть передач завершалась, часть — зависала |
| 3 | Обходной путь в `diskio.c`: ручная проверка регистра **NDTR** (остаток байтов DMA) вместо доверия состоянию HAL | Позволял «дождаться» реального конца DMA, но не давал стабильности: состояние HAL оставалось BUSY, поведение при повторных операциях непредсказуемо |

Вывод по §3: ни одна мера не лечит саму гонку внутри `HAL_SD_IRQHandler` — она устраняется только правкой HAL-кода (вне проекта) или отказом от DMA-API.

## 4. Решение и обоснование

**Решение:** полный возврат к блокирующему режиму (`diskio.c`: `HAL_SD_WriteBlocks` / `HAL_SD_ReadBlocks`, timeout 1000 мс, `HAL_IWDG_Refresh` после каждой операции). Текущий код HIL-1/HIL-2 остаётся эталонным.

**Почему потери производительности нет:**

1. **FatFs (R0.12c) — синхронная библиотека.** `f_write`/`f_read` вызывают `disk_write`/`disk_read` последовательно из главного цикла; асинхронность DMA не даёт выигрыша, т.к. следующий вызов всё равно ждёт завершения передачи. Узкое место — скорость самой SD-карты (миллисекунды на чанк), а не CPU.
2. **Тайминги вписываются с запасом.** Коммит чанка: `f_write(12 КБ)` ≈ 3–10 мс + `f_sync` ≤ ~200 мс (worst case, оценка из `main.c`). IWDG таймаут ~1.5 с — блокирующая передача на порядок короче; watchdog кормится после каждой операции.
3. **Блокирующий режим уже верифицирован сквозными тестами:** HIL-1 (`LOG0001.VIB`, CRC header + CRC32 OK) и HIL-2 (31 чанк / 63 488 сэмплов, 0 пропусков за ~40 с). DMA-вариант не даёт ни скорости, ни надёжности сверх этого.

## 5. Выводы и уроки

1. **DMA-API HAL для SDIO на F4 (STM32F4xx HAL) считать непригодным** до исправления гонки DATAEND/DMA в `HAL_SD_IRQHandler`. Не возвращаться к этой теме без проверки ревизии HAL.
2. Если асинхронная запись понадобится в будущем — путь: собственный тонкий драйвер поверх SDIO (управление FIFO + DMA с собственным обработчиком завершения) либо ожидание исправленной ревизии HAL. Обходные пути через NDTR не являются надёжной основой.
3. Базовая конфигурация шины при откате **не менялась**: 1-bit, `ClockDiv = 16` (фикс BUG-2 из HIL-1), детект карты PA8 (Active LOW).
4. Документ фиксирует решение: **SDIO — блокирующий режим; FatFs — синхронный слой; IWDG — защита от зависаний.** Любая будущая оптимизация хранилища должна отталкиваться от этого базиса, а не от DMA-попытки.
